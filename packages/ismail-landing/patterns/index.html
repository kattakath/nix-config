Recurring patterns

The same handful of shapes keep earning their place across production systems. Each one turns a class of incident into an invariant the code cannot violate.

These aren't slideware. Every pattern below is cited to a system I actually shipped — the problem it answers, where it runs, and the guarantee it holds. For the measured outcomes those systems produced, see the evidence ledger.

The pattern matrix

Problem → System → Invariant
Six patterns, each grounded in a real system
Pattern The problem it solves Where I shipped it The invariant it enforces
Idempotency as a contract Idempotency At-least-once delivery and automatic retries mean the same message can be processed twice — double-charging a customer, indexing a document twice, re-firing a webhook. Takeoff — a platform-wide contract across the whole AWS Lambda fleet at Infin8. Running a handler twice on the same input has the same effect as running it once. A duplicate is a no-op, never a second side effect.
Advisory-locked migrations Migrations Two deploys landing at once can run the same schema migration concurrently — interleaving, deadlocking, or corrupting the database. Takeoff — Aurora Serverless v2 behind an IAM-authenticated RDS Proxy at Infin8. A migration takes an advisory lock before it runs. Exactly one migration executes at a time; it cannot race another deploy.
Fail-closed cost governor Kill-switch An autonomous inference fleet can silently run up unbounded provider spend before a human ever notices the graph. Takeoff — the Document-AI worker fleet (batch OCR / vision on LiteLLM) at Infin8. When the budget is exceeded — or the check itself can't be evaluated — the fleet stops. The default is denial, not "keep going".
Tenancy by construction Isolation In multi-tenant SaaS a single flawed authorization check can let one tenant read or act on another tenant's data. Takeoff — dual Cognito pools with JWT audience isolation and token authorizers at Infin8. A token minted for tenant A is rejected for tenant B by its audience. Cross-tenant escalation is structurally impossible, not merely checked.
Keyless CI GitHub OIDC Long-lived cloud credentials stored in CI are a standing theft surface — one leaked secret and an attacker holds your account. Takeoff deploys via GitHub Actions OIDC at Infin8; this site's own nix-config repo publishes to FlakeHub over OIDC with no stored token. No long-lived secret lives in CI. Every deploy authenticates with a short-lived, workload-scoped OIDC token, staging a required gate.
Reuse over rebuild Less surface Custom infrastructure you build is infrastructure someone has to keep maintaining — forever, after you've moved on. The public nix-config mono-repo — a bespoke ~40-file engine deleted in favour of one maintained dependency. Build to learn a domain, then delete what an off-the-shelf tool already does. Every line kept must earn its maintenance cost.

The common thread

Why these six

Incidents become invariants

Every postmortem ends as a guard the CI pipeline enforces — idempotency, an advisory lock, a fail-closed default — so the same failure cannot recur quietly the next quarter.

Structural over procedural

I prefer a boundary the system cannot cross to a check a reviewer has to remember: isolation by token audience, denial by default, one migration by lock. The guarantee lives in the shape, not the vigilance.

Public and reproducible

This very site is served from that one declarative Nix mono-repo. The patterns aren't diagrams on a slide — they run in production, and the ones I own personally are open to read.
