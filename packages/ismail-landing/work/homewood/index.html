I inherited it abandoned. I left it a platform.

Case study · 02
Shipped Oct 2017 – Jul 2024 Homewood Health · Senior Software Engineer

Canada's national digital mental-health platform — EFAP and CBT — came to me abandoned and undocumented. Over nearly seven years I rebuilt it into something that stays up, signs people in safely, and doesn't fall over when it moves.

This is a real, shipped body of work, so I hold it to the same honesty rule as the rest of this site: every figure below is something I did and can name. Where a number is my own operational measurement rather than an externally audited one, I grade it as self-measured rather than dress it up as a certified fact.

The problem

Beat 01 — Problem

An abandoned codebase, still in people's hands

The platform was a MEAN-stack application that had been left without documentation and without an active owner — yet it was the front door to counselling and CBT for employees across the country. Inheriting software like that means first learning how it works at all, because nobody who did is still around to ask.

Mental-health software has to be dependable

This isn't a marketing site. People reach for EFAP and CBT tools at hard moments, often through an employer's single sign-on, sometimes across a partner organization's identity. Reliability, safe authentication and clean access are not features here — they are the reason the thing is allowed to exist. Reaching 100k+ users only raised that bar.

The system

Beat 03 — Architecture

Users arrive through their employer's identity — the Microsoft Identity Platform over OAuth 2.0 PKCE, or one of the SAML 2.0 partner federations. Authenticated requests hit a migrated Next.js frontend that preserves the original UI/UX and API contract, backed by the application tier. State and assets live in an AWS data tier reached over VPC — EC2, RDS, S3 and CloudFront — with the whole footprint described in Terraform and shipped through CI/CD.

Identity & federation

Sign-in is rebuilt on OAuth 2.0 PKCE against the Microsoft Identity Platform for 25,000+ users, with SAML 2.0 federation configured across 5+ partner organizations so each brings its own IdP.

Frontend & app tier

The AngularJS frontend was migrated whole to Next.js on framework EOL, deliberately preserving the UI/UX and staying API-compatible so the backend contract — and the users' muscle memory — didn't have to change.

Cloud & delivery

The footprint moved DigitalOcean→AWS (EC2, RDS, S3, CloudFront, VPC) described in Terraform, with zero downtime, and CI/CD, monitoring and backups underneath — the deploy path cut from four hours to twenty minutes.

Tradeoffs

Beat 05 — What I chose, and gave up
Inheritance

Rescue over rewrite

The app was abandoned and undocumented — the tempting move is a clean-sheet rewrite. I chose to revitalize the running MEAN-stack system to production-ready instead, keeping real users served throughout. Slower and less glamorous than greenfield, but it never took the platform offline to rebuild it.

Users stay servedLegacy carried forward
Frontend

Migrate on EOL, preserve the surface

When AngularJS hit end-of-life I moved the whole frontend to Next.js, but deliberately preserved the existing UI/UX and kept the API contract unchanged. That gave up the chance to redesign — and bought a migration users didn't have to notice and a backend that didn't have to move in lockstep.

No relearningNo redesign
Cloud

DigitalOcean → AWS, zero downtime

Lifting the platform to AWS (EC2, RDS, S3, CloudFront, VPC) unlocked managed data services and a CDN, at the cost of a more complex footprint to reason about. Describing it in Terraform made the move reproducible, and holding the line on zero downtime meant the migration was invisible to the people using it.

Zero downtimeMore surface
Identity

Standard OAuth/SAML, not homegrown

Auth was rebuilt on OAuth 2.0 PKCE with the Microsoft Identity Platform and SAML 2.0 across partners — reusing the standards rather than inventing a login flow. That means living with each partner IdP's quirks and troubleshooting federation, but never owning the security of a bespoke auth system on a health platform.

Standards-basedPer-partner config
Delivery

Invest in the pipeline, not heroics

Rather than keep shipping through a four-hour manual deploy, I built CI/CD, automated testing and containerization up front. That's real setup cost paid once — and it turned releases from a four-hour ordeal into a twenty-minute routine, with monitoring and backups so failures surface instead of hiding.

4h → 20minUpfront cost

What I'd do differently

Beat 06 — Honest retrospective

Document while learning, from hour one

Inheriting an undocumented system, the single most valuable thing is capturing how it actually works before the knowledge lives only in my head again. I'd formalize that documentation from the first day of the rescue, so the platform can never be "abandoned and undocumented" a second time.

Make uptime externally verifiable

99.5% uptime is my own operational measurement — which is exactly why it's graded self-measured here. Next time I'd stand up independent, third-party monitoring from the start so the reliability number is auditable rather than self-reported.

Federate the partners sooner

SAML 2.0 across 5+ partner organizations was configured and troubleshot as it grew. Knowing that pattern now, I'd invest earlier in a repeatable onboarding path for a new partner IdP, so each federation is a checklist rather than a fresh troubleshooting round.
