The platform beneath an AEC-estimation AI.

Case study · 01
Current Mar 2026 → Infin8 Information Technologies

Takeoff turns construction PDFs into structured quantity estimates. I own the backend and the cloud beneath it — the multi-tenant, billable, AI-heavy machine the product runs on.

This is a live build, so I hold it to the same honesty rule as the rest of this site: I describe what is shipped in production, and I do not quote outcome numbers I can't yet source publicly. Where a figure would belong, I say it's not public rather than invent one.

The problem

Beat 01 — Problem

Estimating is manual, per-drawing work

In architecture, engineering and construction, an estimator does takeoff — reading quantities off construction drawings, page by page. The drawings arrive as PDFs. Takeoff's job is to index those pages, detect frames, and lift the measurements with AI so the estimator isn't doing it by hand.

It has to be a product, not a script

Many construction firms, each in an isolated workspace; document AI that is expensive per page and must be metered and billed; a subscription lifecycle that turns that usage into revenue; and collaboration that stays live while a team works a job together. That is a multi-tenant SaaS spine — and it's the half I own.

The system

Beat 03 — Architecture

A Python 3.12 monorepo deploys as FastAPI on AWS Lambda through multi-stack AWS CDK. Every request enters through WAF and a token authorizer backed by two Cognito pools; realtime collaboration rides a separate WebSocket API fanned out through Valkey; state lives in Aurora Serverless v2 reached only through RDS Proxy. Billing and the Document-AI worker fleet hang off the app tier.

Edge & identity

WAF fronts the REST API; a token authorizer validates JWTs against two Cognito pools before any handler runs. Tenancy is decided at the token, not in application branches.

App & data

FastAPI on Lambda talks to Aurora Serverless v2 only through RDS Proxy with IAM auth — no static DB credentials, connections pooled so bursty invocations don't exhaust the database.

Billing & Document AI

Stripe carries the free/trial/paid lifecycle with usage metering, overage and a reconciliation pass. Document AI runs as agent + index workers behind LiteLLM, cost-governed and fail-closed.

Tradeoffs

Beat 05 — What I chose, and gave up
Compute

Lambda over long-lived containers

FastAPI on Lambda scales to zero and bursts per tenant, so I don't pay for idle and don't hand-tune autoscaling. The price is cold starts and execution limits — which is exactly why the heavy Document-AI work is pushed off the request path onto a worker fleet.

Scale-to-zeroCold-start tax
Data

RDS Proxy in front of Aurora

A serverless fleet will open connections faster than a database can absorb them. RDS Proxy pools them and IAM auth removes stored passwords entirely. The cost is another managed hop and the Serverless-v2 capacity floor — I traded a little baseline spend for connection safety and no secrets in the fleet.

No DB passwordsExtra hop
Tenancy

Two Cognito pools, not app-level checks

Isolation lives in the token audience, so a handler physically cannot see another tenant's scope. That buys structural safety at the cost of running and reasoning about two pools and their authorizers — worth it, because the alternative is trusting every future code path to remember the check.

Isolation by constructionMore moving parts
Billing

Reconcile, don't trust the webhook

Stripe webhooks are at-least-once and occasionally missed, so I treat them as hints and run a reconciliation pass over the source of truth, with idempotency across the fleet so retries never double-charge. More code than a naive listener — but money that always balances.

Exact billingReconciliation cost
AI cost

LiteLLM with a kill-switch

Routing Document AI through LiteLLM abstracts the provider and gives one place to put a fail-closed cost governor. The extra indirection earns provider portability and a hard ceiling on spend — the worker fleet stops rather than runs the bill up.

Provider-abstractedFail-closed
Delivery

Keyless CI over stored credentials

GitHub OIDC means no long-lived cloud keys anywhere in CI, and staging is a required gate before prod. It's a stricter pipeline to set up than a stored access key — and it removes the single worst secret to ever leak from a repo.

No stored keysStaging gate

What I'd do differently

Beat 06 — Honest retrospective

Instrument outcomes from day one

The most honest gap on this page is the empty outcome column. Next time I'd make per-tenant latency, cost per document and SLO tracking first-class from the first deploy, so the claims are provable — the way the rest of this site insists.

A ledger, not a reconciliation pass

Reconciliation is a safety net over Stripe. I'd lean further toward an event-sourced usage ledger so a bill is derived from immutable events rather than reconciled after the fact — fewer moving parts to trust for correctness.

Warm the latency-sensitive edges

Scale-to-zero is the right default, but a few endpoints feel the cold-start tax. Once real traffic shape is known I'd weigh provisioned concurrency or a thin always-warm tier only where it earns its keep — not blanket across the fleet.
